# Local bridge and recovery

Ribosome uses JSON-RPC 2.0 requests and responses, framed as one UTF-8 JSON value per newline. Stdout is protocol-only; diagnostics use stderr. The protocol is `ribosome/1`, the build is `0.1.0`, and the Pi adapter pin is `0.85.1`. Handshake mismatch fails before dispatch.

Both peers continue reading while a request is pending. Frames are limited to 1 MiB and active/outbound requests to 32 per peer. Artifact reads return at most 65,536 bytes per request; local artifacts are capped at 16 MiB. UTF-8 offsets are byte offsets. Requests have string IDs and never share their identity with an effect operation by implication.

Worker-capacity waiting accepts cancellation and is bounded by the root deadline. Handshake waiting is bounded by both its five-second timeout and the root deadline, and accepts cancellation before dispatching the agent.

Schema validation occurs on incoming arguments and outgoing results in both languages. Missing optional fields are omitted; `null` is rejected unless a schema explicitly permits it. Record schema version, protocol version, and motif/implementation version are separate. Large counters and millisecond timestamps use decimal strings. Unknown measurements omit `value`; they are not encoded as zero.

The supervisor binds the pipe to a run and its stored grant. Worker tool arguments have no scope or grant override. Unknown methods and extra fields are rejected. The trusted Pi adapter reads `session.grant` and supplies that authority as context; the model cannot call this method or replace its grant. Accounting, checkpoint and activity methods also belong to the adapter. There is no generic database endpoint. The record tool presents the selected operator's body schemas, generated from the same contracts that Rust validates.

The trusted Pi adapter incrementally saves completed messages with `session.context.append`. Rust atomically retains the raw message and publishes its visible `agent_message` evidence. Provider reasoning and transport signatures are excluded from visible activity. Context positions make retransmission idempotent. The adapter supplies typed record/event/artifact references from actual tool responses, including observed versions; Rust conservatively inherits every earlier source in the segment for subsequent messages. The model cannot call context methods or remove that inherited lineage. For direct record observations without a matching retained artifact, Rust adds the corresponding immutable activity event to the segment sources. An unbacked stale revision is rejected with an instruction to rebuild from fresh evidence. Rust also attaches the producing context's sources to `record.submit`, so a model-authored memory cannot become independent by omitting its inputs. Activity retains the most restricted split visible to its run. A worker's evidence tool excludes its own active message stream. Host receipts remain authoritative for effects; role-authored messages do not establish successful execution.

`artifact.read` defaults to `required_freshness=current`. It returns a retained `snapshot_id`, exact artifact version and the requested freshness requirement. A later revision makes a context that needs that observation current ineligible for continuation; the host starts a clean segment with the owner task and real operation references. `required_freshness=historical` permits an older accessible version. It does not claim that those bytes describe the current artifact. A `snapshot_id` reads only its retained byte window; it cannot retrieve bytes that were never observed. A current read of an outdated snapshot is rejected with an instruction to reread the artifact.

Deletion observed by the host writes artifact tombstones, advances the scoped policy generation and queues cleanup in one transaction. Historical reads are then denied too, including records/events derived from those snapshots. Cleanup redacts development snapshot content, context copies and derivatives. Recreating the path does not revive deleted snapshots. Snapshot reads retain client/project, path, split and branch ownership checks.

Messages are scoped to their existing immutable communication grant. `message.send` commits its body and a metadata-only `communication` event together; the event inherits the sender's current context and summary sources. `message.inbox` checks that ancestry before parsing or delivering the body. Only available deliveries consume attempts, and a failed batch update rolls back every attempt in that batch. The receiver's retained tool observation includes each message event, so receiver interpretations inherit sender sources too.

Run completion commits its summary and a metadata-only `run-result` event together. Inspection returns `result: null` and `result_available: false` when the saved summary's sources are unavailable. Delivery through Supervisor and attachment completion also withholds that text; the recorded disposition remains unchanged. Repeated finalization of a non-running run does not replace its result. Legacy summaries and message bodies without source evidence are withheld rather than assigned invented provenance. Scoped deletion clears legacy development copies, including embedded checkpoint messages, while preserving operation IDs, other clients and protected copies.

## Effects

1. The TypeScript tool wrapper derives a stable operation ID from the run and Pi tool-call ID.
2. Rust commits a prepared intent with the action and grant snapshot.
3. Host preflight checks authority and versions. Rust persists the dispatch marker, potential live writes and invalidation generation before adapter execution. The adapter repeats its checks.
4. Rust captures the adapter outcome durably, then one transactional finalizer publishes the receipt/event, registers any branch and updates dependent validity. Internal phases are `prepared`, `dispatching`, `observed` and `finalized`. A failed finalization keeps the captured outcome for retry.
5. Pi receives the receipt as a tool observation and decides its next step.

A repeated operation ID with different arguments or a different grant is rejected. A repeated identical completed operation returns its existing receipt. Timeout or pipe failure is not authorization to retry it.

Settled receipts expose `evidence_ref`, the exact executor event ID accepted by record provenance. `operation_id` identifies the effect for lookup; it is not a source event ID. Event IDs use a bounded hash so a maximum-length operation ID can still produce valid evidence. Pending intents have no evidence reference.

`ActionReceipt.validations` contains host-authored `ValidationEvidence`: check name, checker fingerprint, owner-policy fingerprint, actual input versions, explicitly validated target and Obligation versions, outcome, source receipt event, branch identity and invalidation generation. A process exit of zero can still produce stale validation if checker code or inputs changed while it ran. `restored_properties` lists the exact Obligation/artifact pairs established by this finalization. `restored_validity` lists an artifact only when all its currently declared scoped properties have current supporting checks. No declared properties means unknown coverage, so an artifact-only checker cannot establish semantic validity. These are historical observations; later reads must establish freshness again. An old successful receipt without captured validation evidence cannot stand in for fresh checks.

Checked application requires explicit target validation, matching checker/policy identities and actual checker input versions against the live recipient, even when the agent omits an input from its intervention. It pins the intervention version and required checker set before checks, then rechecks owner policy, cancellation and writer handoff before dispatch. Only the selected artifact is applied; other checked branch inputs must already match live state. The shared finalizer repeats transfer checks, records supported properties and clears the applied artifact's invalidation only with complete declared property coverage. Unvalidated consumers stay stale. If a source, checker, policy or intervention changes before delayed finalization, the application remains a recorded historical success but `restored_validity` is empty and fresh authorized checks are required.

A captured adapter outcome supports `outcome_basis: "execution_established"`; it can establish either a successful or failed execution. Preflight denials and failures before the dispatch marker use `not_dispatched`. Errors after that marker remain `unresolved` unless a captured adapter outcome establishes what happened. Matching intended edit/application bytes without a captured outcome produces `current_postcondition_observed` with status `unknown` and a distinct `action_reconciliation` event. It does not establish dispatch, causation or mandatory checks. Potentially affected consumers are invalidated. Unsettled live effects retain write ownership. Unknown receipts without a host settlement stop continuation and handoff release. Repeated lookup and finalization return the same receipt without repeating adapter execution or validity updates. Exactly-once external effects are not promised.

Live check finalization clears only explicitly validated paths whose observed input versions still match and whose invalidation generation is no newer than the check's dispatch generation. A known later source invalidation survives even if bytes return to their former values. This generation tracks Ribosome invalidations; it does not detect an unobserved external change-and-change-back. Checker/policy/input/target certificates now support checked-application transfer. The artifact generation remains stored after its aggregate stale flag clears, so an older delayed finalizer cannot replace newer property evidence. Host tool configuration binds `validated_properties` to exact `Obligation` record versions and target paths included in `validates`. Any record revision requires an updated host binding and a new check. Checks attach mechanical evidence without changing the obligation's authored state. Independent current checks can establish separate properties of the same artifact version; unknown or unsupported coverage remains conservative. Legacy terminal receipts retain their status and have no invented `outcome_basis`; their status alone is not execution or validation evidence.

`effect.inspect` and `effect.settle` belong only to `ribosome-host/1`, not to the worker RPC or Pi tool list. Inspection returns the historical receipt, its content version and current versions of all granted live workspace paths. Settlement pins that receipt version and the full workspace observation, requires the owner to attest `executor_stopped: true`, and records a reason plus optional scoped source references. The owning run must be stopped. The endpoint does not stop or independently inspect an external process; the trusted host must establish stoppage before calling it. Workspace comparisons have the cooperative local adapter's current-content guarantee.

A settlement event, conservative invalidation of possibly written artifacts/consumers and the ownership release commit together. Settlement preserves the original execution outcome. Source deletion can subsequently redact copied receipt and event content. `ActionReceipt.settlement` is a separate persisted owner decision, joined into lookups and run inspection. `ActionReceipt.content_available` reports whether copied content is authorized. New receipts capture source context before dispatch, and completion events inherit that context. Unavailable or unverified sources produce `content_available: false`: action content, output details and validation claims are withheld while operation status and outcome basis remain intact. A fresh status-only lookup does not inherit withheld content; earlier retained full-content lookups remain subject to withdrawal. Internal reconciliation retains its operational inputs until finalization. Legacy receipts without verified lineage cannot supply model-facing content. Its presence never changes `status: unknown` into success or supplies missing `outcome_basis` or validation. Repeating the identical decision returns the recorded observation; a changed decision conflicts. Settlement can finish after grant expiry, but does not authorize new effects under an expired grant. Each unknown effect needs its own settlement before all ownership fences can clear. A retained lookup inherits both original and settlement event ancestry. Legacy unknown receipts without an event ID can be settled by pinning their stored content version.

`artifact.validity` takes a live workspace `path` and returns its exact artifact version, observation time, invalidation generation and visible property assessments (`validated`, `stale`, `unproven`). Each assessment pins the current Obligation version and includes supporting receipt event IDs only when validation is current. It rechecks source access, checker/policy identity and actual input/target versions. A retained result is historical; obtain a fresh assessment before relying on it. Result ancestry includes the property records, supporting events and a version-only artifact snapshot. Retirement/deletion denies affected retained results. Version-only snapshots support binary artifacts and cannot be read as text chunks. An empty property list establishes no semantic coverage.

The worker checkpoints through Rust before and after tool transitions. On restoration, the adapter repairs incomplete tool-result sequences using host receipt lookup. For non-effect tools, `tool.result` retrieves the original authorized observation by run and tool-call ID. If no result was retained, the adapter preserves the missing-result status and lets the agent request fresh evidence; it never replays the tool to fill that slot. Unknown effects require a separate stopped-executor settlement from the owning host before continuation. Their original outcomes remain unknown.

`continuation.read` accepts `{kind: "obligation" | "effect" | "work", after, limit}` and returns bounded reference metadata, `next`, `complete` and `evidence_cursor`. The host binds the current run. It lists previously observed, accessible Obligation records whose declared state is not satisfied, all that run's operation IDs and its direct child-work IDs. The cursor advances across unavailable obligations, so an empty page need not be complete. Pages inspect current state rather than freezing an inventory; restart from `after: "0"` when rechecking revised obligations. References establish neither completion nor current validity. Retrieve their current record, receipt or work status before relying on contents. The evidence cursor is the last checkpointed evidence-read position, not a claim that every relevant event was inspected; preserve the original filters or restart evidence selection when those change. Clean continuation segments include the first 20 references of each kind and instructions for paging the remainder. No separate continuation inventory is persisted.

`pi-0.85.1/2` checkpoints contain a context descriptor, an empty legacy `messages` array, pending operation IDs, event cursor and the pinned profile/operator/provider/model. The descriptor is limited to 256 KiB; the bridge remains limited to 1 MiB. Rust retains the transcript separately and returns bounded pages of its recent complete exchanges, with the owner instruction. Worker and host negotiate `context.v2`, `context.sources/4` (record, event, artifact and message-derived observations with pinned record ancestry), `context.compaction/1` (metered semantic summaries) and `context.results/1` (retained tool observations). The descriptor includes the latest committed summary reference and its covered sequence frontier. Version 1 checkpoints and context segments predating source format 4 retain their raw observations in SQLite, but unsupported text is withheld by checkpoint/context APIs; continuation starts from the owner task and real operation references.

`session.context` authorizes stored record/event/artifact sources on restoration and before each provider request. Retirement, deletion, expiry or scope/split access loss makes the affected segment unavailable. Rust creates an explicitly linked clean segment from the owner task and recent operation IDs; the adapter replaces both Pi's loop context and public state. It does not send withdrawn text for cleaning or manufacture successful tool results. Unknown effects still prevent continuation. Authorization uses a SQLite snapshot; withdrawal acknowledged before that authorization is respected. A withdrawal after authorization cannot revoke the already authorized request or erase content already sent to a provider. Errors from authorization stop dispatch.

Before older exchanges leave the provider context, `session.compaction.prepare` selects a durable prefix window of at most 20 messages and normally 180,000 visible bytes. `session.compaction.read` reauthorizes that window, the owner task and its predecessor summary; provider reasoning/signatures are excluded. A separate Pi call has only `commit_summary`, with no task tools. It synthesizes at most 16 KiB of UTF-8 text. Its `model.permit.compaction_id` binds the call to the prepared window, and the same root grant accounts for its calls, tokens, costs and unknown usage.

`session.compaction.commit` requires complete settled usage from that window's permit, an unchanged predecessor and eligible input sources. Rust records the summary as an attributed `pi-compactor` event and derives source edges from the supplied context and predecessor summary. The model cannot drop those edges. The summary/event commit is atomic and idempotent. A crash before commit can retry the pure synthesis under another charged permit; a committed summary is discovered after restart even when the last checkpoint predates it. Neither path replays an external effect. Active evidence retrieval excludes the run's own compactor events as well as its ordinary Pi activity.

The main provider receives the owner request, the authorized summary and recent complete exchanges within 180,000 serialized message bytes. This provider view does not replace the retained transcript. Withdrawal before compaction authorization/permit blocks its dispatch; withdrawal during an in-flight call prevents committing its result. The adapter opens a clean segment without passing the withdrawn summary to another model. Provider errors and incomplete compaction stop continuation; budget exhaustion remains `exhausted`. Cancellation reaches the compactor and retains incomplete usage reservations. If inline tool results collectively exceed the provider window, their provider projection contains readable result references while preserving every tool-call ID. This projection is mechanical and makes no semantic claim about their contents. A required exchange that still exceeds capacity fails explicitly. Complete obligation references and broader copied-store cleanup remain R1 work.

Usage, checkpoints, visible activity and receipt lookup can settle after cancellation or a deadline. This does not permit additional model calls or effects. Unknown model usage retains its reserved budget.

The trusted adapter dispatches model tools through `tool.call` with a stable call ID, an allowed method and validated arguments. Rust executes the existing tool path, then atomically retains its original JSON result and source ancestry in `artifact_snapshots` before returning it to Pi. Calls with the same run/call ID return the retained observation; different methods or argument hashes conflict. This result cache is separate from effect receipts: recovery still reconciles an effect through `action.lookup`, and a failed result-retention write does not undo an effect.

Results up to 32 KiB are returned inline. Larger results return a UTF-8 excerpt of up to 4,096 bytes, the total byte count and an immutable `ribosome-result:` artifact reference. Use `artifact_read` on that path to read further bytes of the original JSON result. Result-artifact reads return at most 8 KiB per call so the resulting chunk stays inline even after JSON escaping; they do not send the reader to another excerpt reference. These reads are historical only; current-state use requires reinspection of the original workspace artifact. Scope, visible split, physical-source path grants and transitive availability apply before content is returned. The prefix cannot address a physical snapshot, and a physical path cannot address a result snapshot. Read offsets are unsigned 32-bit byte offsets; chunk and bridge size limits are unchanged. Source deletion denies the result and derived reads immediately; cleanup later clears their retained payloads. Full result payloads are retained in Rust. Provider requests contain inline content, excerpts or readable result references; host-only source metadata is omitted.

Record, event and tool-result writes capture the ancestry of referenced mutable records in their own source edges. A later revision can replace the current record's dependencies without changing those older observations. Capture follows mutable record chains and retains references to immutable events/artifacts; it does not expand the entire event history. Released access edges remain released, and unavailable ancestors still deny access. ID-only ancestry does not acquire an invented historical version. A tool response whose record version changes before retention fails rather than pairing old content with current ancestry. Content and captured edges commit together.

## Training export files

`training.export` returns its existing host filesystem `path` and `count`, plus an immutable `artifact` reference using `ribosome-export:`. The JSONL product retains its original observed, reexecuted or synthetic label. Export checks traverse typed record, event and artifact edges, including released access edges; protected ancestry cannot enter training data. The snapshot retains the entire reviewed source closure and exact observed versions, so a later revision of a selected record cannot detach the earlier exported bytes from their sources.

Use `artifact.read` on the managed reference for authorized reads. These reads require the current scope, export capability and source closure; they verify the file against its recorded digest and return at most 8 KiB per call. Exports are historical products. Neither a physical workspace path nor a `ribosome-result:` reference can address an export snapshot. Products are limited to 16 MiB; larger selections must be split.

The snapshot manifest commits with `available=0` before file creation. Publication rechecks sources under the writer transaction, writes and syncs the file, then commits availability. Failed or interrupted publication never becomes readable through the API. Runtime startup queues unfinished manifests for cleanup. Tombstones deny ready products through ancestry while physical deletion is pending or failed. Cleanup removes only recorded filenames in the bound export directory; a missing file is an idempotent retry. A failed SQLite commit after unlink can leave metadata awaiting retry but cannot restore deleted bytes or authorize them. Cleanup status reports the remaining work.

The returned filesystem path is a host-owned delivery copy, not an authorization endpoint. Direct filesystem access can read it until physical cleanup removes it; callers needing current source authorization must use the managed reference. Files copied elsewhere, legacy exports without manifests, backup/WAL pages and content already sent to providers require separate owner retention handling. Migrating legacy exports remains R1 work; unknown files are neither deleted nor assigned fabricated source lineage.

## Shared resource accounting

Both peers must negotiate `budget.allocations/1`. Each run is bound to a host-owned allocation beneath its immutable grant. `AgentRunRequest.parent_allocation_id` may select an existing allocation in that grant; scheduled work must use its recorded parent. Worker permit arguments cannot select an allocation or grant. Allocation IDs, parents, causal IDs, purposes and ceilings are immutable across retries. Trees are bounded to 64 levels.

`model.permit` reserves calls, tokens and accounting cost atomically against every ancestor. The current Pi adapter supplies a stable `call_id`, then calls `model.dispatch` before provider transport. Identical permit requests return the original permit; changed requests conflict. A repeated dispatch is rejected, including after a lost acknowledgement: it does not authorize another provider call. `model.permit.lookup` retrieves the original permit by call ID. The Pi adapter uses this lookup after a lost reservation response, then asks Rust to release it if still undispatched; it does not request replacement capacity. `model.release` refunds only a provably undispatched reservation and is idempotent. Dispatched calls with unknown usage retain their allowance across restart. `model.usage` settles once from the trusted adapter; identical reports are idempotent and conflicting reports fail. Legacy callers without call IDs are conservatively treated as already dispatched.

`budget.status` returns the bound allocation, subtree usage and remaining capacity limited by every ancestor. Host APIs `Store::root_budget_status`, `budget_status` and `run_budget_status` use the same representation. Usage distinguishes settled totals, outstanding reservations, undispatched calls and dispatched calls with unknown usage. Child ceilings do not allocate new money; sibling spending reduces their shared available capacity. A status response is an inspection snapshot; only an atomic permit authorizes dispatch. Denied action attempts still consume the action counter. Follow-up work consumes the same root work count and depth limit and gets a causal child allocation. Completing a parent run does not revoke already queued descendants; cancellation, failure and exhaustion prevent further provider, effect and child-work dispatch beneath that parent. Previously issued observations can still settle.

Studies declare their experiment, arm/repetition and case allocations in the same short transaction as the frozen study, before evaluator execution. Each `EvaluationTask` carries its allocation ID and effective remaining capacity. A Rust `Evaluator` receives an `EvaluationAccount` for real permit, dispatch, release and usage operations. The account denies new permits and dispatch after cancellation, while accepting settlement and safe release of prior work. `provider_usage_is_metered()` defaults to false; only a trusted adapter that meters every provider call, or makes no provider calls, may return true. The one-shot command evaluator cannot participate in that permit exchange and reports incomplete usage coverage. Its output cannot establish billing evidence or strict aggregate-budget qualification.

A study retains every planned evaluation, including failed, exhausted, cancelled and not-started cases. A local case exhaustion leaves other funded cases runnable; shared-budget exhaustion or cancellation stops further dispatch. Missing or exhausted cases yield an incomplete, inconclusive result. Allocation dispositions preserve the actual stop cause; a failed checker result from a completed evaluation remains a measured failure, distinct from failure to execute the evaluator. `planned_evaluations`, `complete` and `usage_complete` describe matrix coverage and instrumentation separately. The matrix is capped at 1,000 evaluations as well as the host policy limit. The whole-agent adapter below meters actual Pi stage executions through this ledger. External source/contrast agents must use the same host permit interfaces to participate in complete accounting.

## Parent waiting and continuation

Both peers require `context.parking/1`. `work.wait` accepts 1–16 unique direct-child work IDs in the caller's grant. It returns their IDs and `wait_required`; it does not block an RPC or create another queue. `work.status` returns the work status and, when authorized, the child's `AgentResult` with its event source. Work identity/status remains separate from availability of the result text.

After a completed Pi tool turn requests a wait, the trusted adapter saves its context and calls `session.park` with the same IDs and a bounded checkpoint. This method is supervisor-only and is not a model tool. The supervisor requires no outstanding RPCs, pending operations, unresolved effects or held repair handoff. Rust validates pinned configuration, context authorization, the retained frontier and completed tool exchanges. Checkpoint, wait IDs and `waiting` status commit in one short transaction.

Successful `session.park` transfers execution ownership to the supervisor, which closes the worker transport without a terminal `agent.run` result or a success reply to `session.park`. Validation errors use ordinary RPC error responses. The supervisor reaps the process and drains issued handles before releasing the slot. A worker must not interpret transport closure as a completed run. Rust's persisted state determines whether this was a committed wait or an interruption.

The existing queue reserves waiting children for that parent's scheduler. Children share the parent's allocation and can recursively wait with the same bounded worker capacity. Once every child is terminal, Rust removes the wait and restores the parent checkpoint in another worker. Host-startup recovery preserves committed waits under interrupted runs; resuming an interrupted parent services its children before making another parent provider call. Host-startup recovery makes orphaned work claims available immediately. If the run result was already saved before the work lease was acknowledged, the scheduler records that existing result without launching another child. Interrupted children remain eligible for recovery within the existing lease and attempt policy.

A child task has a metadata-only source event derived from the requesting run's context and explicit evidence. That event is checked before child dispatch and included in retained context ancestry. Parent history is not copied into the child context. Completion events carry the child's lineage, which is checked before result delivery. Schema-16 work without a source reference remains stored but requires owner review before a fresh request; migration does not invent task authority.

Cancelling a wait or reaching its deadline closes queued child allowances and retains the appropriate cancelled/exhausted work status. An already-running child receives cancellation through its existing supervisor owner; issued work and unknown usage retain their owners and liabilities. The parent may become terminal before an independently owned child settles. Its fence remains held until that owner's actual settlement, and a closed ancestor denies new dispatch. Interrupted parents preserve their wait for explicit continuation.

## Evaluation and persistence

SQLite uses WAL, a busy timeout, explicit operational tables and FTS5. Schemas 1–20 migrate transactionally to schema 21 after a consistent database backup; unknown newer schemas are rejected without rewriting their version. Schema 3 stores declared source relationships, tombstones, a source-policy generation and retryable derivative-cleanup jobs. Record lookup, search and reference checks enforce ancestor availability while cleanup is pending or failed. Indexes remain derived from scoped records. Schema 4 adds retained context items, explicit segment predecessors and typed record/event source references. Context reads and inspected tool summaries also enforce source availability. Schema 5 retains scoped artifact read windows and their exact versions. Runtime reads and context authorization refresh those observations through the host adapter. `Store` holds the last observed filesystem availability; it does not watch the filesystem. Workspace I/O uses the host adapter. Runtime also binds the store to its managed export directory for file cleanup. Schema 6 adds prepared/committed summaries, predecessor/coverage references, attribution from context items and compaction-specific permit bindings. Deletion cleanup redacts dependent summary payloads; source checks deny them while cleanup is pending or failed. Schema 7 persists traversal worklists and edge cursors. Each cleanup batch limits graph work, retains completed progress across failures and atomically saves each node's redaction with its cursor. Late source edges reopen affected jobs. Ancestry remains after payload removal, so late derivatives stay unavailable. Schema 8 adds immutable tool-result payloads, run/call identity and argument hashes to artifact snapshots; legacy snapshots retain their original contents and are not represented as tool results. Schema 9 adds source evidence for messages and run results. Earlier message-result artifacts become unavailable because they lack sender lineage; migration preserves their raw bytes. Schema 10 adds managed export filenames to artifact snapshots. Schema 11 captures mutable record ancestry for existing observations whose retained revisions support it. Legacy copies referencing a revised record with no matching observed version are tombstoned conservatively, with their original payloads preserved. Already pinned export products retain their reviewed closure. Unsupported older segments rebuild under source format 4. Protected evaluation evidence, admission records and protected events retain their payloads under the existing policy; traversal still reaches their ordinary derivatives. Schema 12 adds effect phases, pinned authority, captured outcomes, potential writes and invalidation generations. Legacy started effects require reconciliation; legacy terminal observations are preserved without fabricated execution or validation evidence. Schema 13 pins checker/intervention preflight identities. Existing captured outcomes remain readable, but outcomes without certificates cannot restore validity. Schema 14 adds per-property support, artifact invalidation generations that survive aggregate restoration, and version-only artifact observations. It preserves older receipts verbatim, imports pending invalidation generations and creates no property evidence for legacy certificates. Schema 15 adds the optional host settlement column. Migration never supplies a settlement for an old unknown outcome. Schema 16 adds allocation ancestry, run/work/effect attribution and provider call identity/dispatch state. Earlier permits remain attributed only to their root grant; incomplete legacy calls remain reserved liabilities, and migration invents neither roles nor safe release evidence. Schema 17 adds `run_waits` and `work.source_ref`; existing work stays intact with no fabricated source reference. Schema 18 adds run timing aggregates and nullable permit dispatch/observation timestamps. Migration preserves legacy usage without inventing measured durations. Schema 19 adds scoped host corpus assignments; existing runs remain unassigned. Schema 20 tracks record-index generations for stable search cursors. Existing record contents and search defaults are preserved.

Experiments persist their frozen cases, starting memory and policy before invoking a host-owned evaluator. Every experiment budget field must fit the run's grant, and execution requires sandbox or apply mode. Agent-authored `model_version` must match the configured run model. Interrupted experiments retain partial evidence and require owner investigation before protected reevaluation. Arm/repetition/case working directories are separate. `EvaluationTask.memory_start` contains snapshots of the declared, accessible Memory records; source event IDs are not starting-memory IDs. An evaluator initializes each new `memory_namespace` from those snapshots. The namespace is an opaque ID, not a path; the evaluator receives the workspace separately, as its current directory for command evaluators. Memory may persist between cases only when `retain_learning_memory` is enabled; it never crosses arms or repetitions. Directories are discarded after the study by default. The initial snapshot is limited to 256 KiB.

A host can register a development-only policy with `allow_generated_development_cases: true` and an empty `case_ids` list. The experimenter then supplies `Experiment.development_cases`, with unique IDs, inputs, source mechanism, synthetic development provenance and proposed `candidate_checks`. Its `case_ids` must match those cases in order. Rust resolves all source references within scope and rejects collisions with registered cases. The host's evaluator, required checks, repetitions and evaluation limit remain fixed. Candidate checks remain proposals. These studies cannot create admission; a separate host-owned acceptance study is required. All templates use the same evaluator path.

No model-provider credentials are passed to registered tools or evaluators. A separately authorized semantic evaluator can implement the `Evaluator` trait or the JSON command interface with its own host-supplied isolation. The supplied reference evaluator executes installed measurement procedures and checks their outputs; it does not interpret arbitrary generated code.

The CLI allows only the selected provider's environment into the worker. Azure uses Pi's `azure-openai-responses` transport with its API key, base URL/resource name, API version and deployment-name map. `request.model` remains the underlying catalogue model ID. Azure credentials and endpoint settings are not included in agent prompts or Rust checkpoints. Missing required Azure configuration fails before model permits are reserved.

The Pi full stream API requires a tool call for each turn, including `finish` for terminal results. Reasoning-capable OpenAI/Azure models receive medium reasoning effort within the existing 4,096 output-token reservation. Non-reasoning models omit reasoning options. Anthropic uses its native `any` tool choice without enabling extended thinking. Provider reasoning stays outside visible evidence.

See [JSON-RPC 2.0](https://www.jsonrpc.org/specification) for the envelope specification. Framing, checkpoints, grant binding, cancellation and recovery are Ribosome conventions, not guarantees supplied by JSON-RPC.

## External harness protocol

`ribosome host` serves the separate `ribosome-host/1` handshake and canonical `x-host-methods` allowlist. It binds each attachment to the host's immutable grant and one source execution. `attachment.events` acknowledges only committed batches; subscription routing commits its work item and cursor together. Attachment ingestion/status, supervised state requests and workspace execution use separate connections to the same SQLite file. Write transactions reserve the writer before reading state to update, avoiding WAL read-to-write upgrade races.

Supervisor routes `action.execute`, `action.lookup`, `experiment.run` and `inventory.admission_request`, including their `tool.call` wrappers, through one executor. Independent evidence, checkpoint and permit requests use the state connection. Owner effect inspection/settlement and writer-handoff release also acquire the executor; they cannot release ownership under an active command. Run restoration acquires that owner before reconciling existing effects. Cancelled queued requests are not dispatched later. Issued blocking tasks remain owned across worker disconnection and caller cancellation; the run becomes terminal only after those handles settle. This changes scheduling, not the bridge protocol or action-accounting rule.

`attachment.feedback` delivers bounded, version-checked finding/proposal references; `attachment.ack` records delivery outcomes. `attachment.steer` records an unknown control intent before the consuming host calls its agent. Acceptance is distinct from later observed effects. Coordinated application additionally requires a held, unexpired generation bound to that repair run; `attachment.release` reconciles outcomes before releasing it. These administrative methods are unavailable to maintenance workers.

See the [integration guide](attachments.md) for wire examples and [operations](operations.md) for startup, detach, restart, schema migration, backup and index rebuild.


## Functional motif records

`Definition.functional_contract` is an optional structured extension: entry inputs and unknowns, authored roles, conditional decisions, observable exit requirements, abstention conditions, exact-version relations, and evaluation questions. Legacy definitions remain readable without this field; absence does not imply a verified policy. Role names are authored descriptions. Rust checks uniqueness and exact definition kind/semantic version for relations, not the validity of their interpretation.

`Occurrence.grounding` binds declared roles to selected `event_refs`, includes incoming context and dependency evidence, and separates local outcome from recognition. `source_reported` means the target event actually lists the source in `parents`; it does not independently prove causation. Other proposed relationships remain `inferred`. Each selected event must fit the occurrence's `run_id/producer` frontier. Local satisfaction or violation needs evidence references. The annotator run belongs to the same root grant and its pinned operator must match the occurrence. Legacy occurrences retain their original shape.

`Discovery` is an immutable investigation record, separate from the Rust work queue. It retains corpus identity, bounded source windows, hypotheses, alternatives, support, contradictions, exact definition versions, occurrences, decisions, questions and participating run IDs. A `no_motif` result may contain no hypotheses or definitions. Supported conclusions require a hypothesis and definition reference, and proposed hypotheses require supporting references. Event citations must appear in the declared windows, whose combined selection is limited to 1,000 distinct events. Run references must belong to the submitting root grant; a supplied work reference must be the submitting run's owned queued work. Nested references participate in scope, split and source-retirement checks.

When an agent submits a grounded occurrence or discovery, Rust checks that its cited source IDs were captured in that run's retained tool observations. A prompt containing an invented ID cannot substitute for a read. This proves a retained retrieval result, not that a provider interpreted it correctly. Owner imports through `Store::submit` do not fabricate retrieval observations. An assigned curator must use the visibility declared by its host corpus; an unassigned curator can submit only retrospective grounding. `evidence.corpus` returns assignment metadata, which does not count as retrieval of the listed evidence. None of these records constitutes implementation admission, checker certification, causal benefit or transfer evidence.

`discovery@1` can produce these records. `contrast-motif@1` is a curator operator for bounded fresh-context investigation through the existing `work.request` / `work.wait` / `work.status` path. It has no separate service or budget pool. Its disagreement and uncertainty remain authored evidence for the requesting curator to inspect.

New `discovery@1` submissions require `Definition.functional_contract` and `Occurrence.grounding`; omitting them cannot select the legacy validation path. Discovery exposes `definition_submit`, `occurrence_submit` and `discovery_submit` with one body contract each. Contrast exposes only `discovery_submit`. These model tools bind the record kind and use the existing Rust `record.submit` method; other operators retain `record_submit`. Discovery's model-facing follow-up tool selects the curator `contrast-motif@1` operator. The contrast operator exposes no follow-up tool. Rust work and depth limits still apply.

The worker `record.submit` path accepts omitted bookkeeping fields: discovery `run_refs` defaults to the submitting run, occurrence `operator` and `grounding.annotator` use its pinned identity, and occurrence/source-window `frontier` is computed from the selected event IDs. Explicit values retain the existing validation. Rust does not add selected events, roles, hypotheses or outcomes. Stored records still contain the full canonical fields. Direct owner imports must supply complete canonical records.


### Bounded event investigation

`evidence.read` now accepts optional `event_refs`, `neighbors`, `kind`, `artifact`, `query` and `through_cursor`. The existing unfiltered read remains the default. `search.query` continues to search records; `evidence.read` with `query` explicitly selects event search. The event query is a literal substring of serialized JSON using SQLite's case folding, not FTS query syntax or a similarity rank. It may scan the scoped event rows; this is not an event-search index or a performance claim.

Filters intersect. `artifact` matches an exact path/version reported by an event. `neighbors: true` requires one to 100 explicit, unique event references and includes their declared parents and children one hop away. All seeds must be visible and source-available before expansion. Results still apply scope, split, active-worker exclusions, source availability, cursor, byte and row limits. A source-reported parent is not independent proof of causation. Targeted pages return only artifact dependency entries touching a returned event's artifact versions; assigned runs use the corpus dependencies and other runs use the current index; their existing `host`, `observed` or `inferred` basis is preserved.

`through_cursor` is an inclusive event cursor ceiling. It does not freeze mutable dependency indexes or establish that the agent never saw later information. An assigned run additionally intersects event selection with its host corpus before pagination and uses the corpus dependency list. It does not return the live invalidated-path list. Continue with the returned cursor even when a page is empty but the cursor advances: unavailable matching rows consume scan capacity without returning their payload or frontier. A non-advancing cursor means this selection currently has no further rows.

### Host corpus assignments

`Store::register_discovery_corpus` registers a scoped `DiscoveryCorpus` with source windows, allowed artifact versions and retained snapshot references, definition versions, dependencies, visibility and limitations. Supply its `VersionRef` in `AgentRunRequest.discovery_corpus` or `Grant.discovery_corpus`. Registration validates access under the owner grant. Reusing a corpus version accepts the same parsed data; changing its evidence selection requires a new version. There is no agent registration method.

Assigned curator runs read selected events and artifact versions, listed definitions and their own work products. Artifact reads require an explicit historical snapshot; another retained snapshot at the allowed path/version is acceptable. Current filesystem reads, unrelated run results, inboxes, live validity, effects, exports and experiments are outside the assigned investigation. Existing scope and source-withdrawal checks still apply. Child curator work inherits the assignment through parking and resume. Resume cannot replace the run configuration.

These restrictions control retrieval through Ribosome. The host must also keep future outcomes and answers out of the curator prompt; an assignment cannot remove information the host explicitly supplies. Actual novel discovery, contrast quality and transfer still require semantic qualification.

### Evaluator copies and source withdrawal

The retained `experiment.run` tool result inherits the experiment record's sources. This allows delivery of its aggregate decision without granting access to protected per-case observations, while source withdrawal also withholds cached copies. Development evaluation records and saved development study inputs are physically redacted during source deletion. Protected evaluation records retain their configured policy and remain unavailable to ordinary context and training export paths.

Study configuration also records temporary workspace ownership before evaluator execution. Runtime cleanup does not interpret an interrupted run as proof that external work stopped. The owner-only Rust `settle_experiment_workspace` method confirms stoppage before deleting interrupted-study files. This metadata is separate from the frozen study inputs used to validate repeat requests; comparison uses parsed configuration values.

Interrupted legacy experiments with no recorded workspace path report cleanup failure. The Rust host owner can confirm that external executors stopped and their copied inputs were removed through `Runtime::confirm_legacy_experiment_cleanup`. That confirmation is persisted as workspace-cleanup metadata and survives development-input redaction. It is excluded from study-input comparisons, cannot produce an evaluation outcome, and is not exposed as an agent tool. Registered workspace cleanup still requires its recorded execution owner to stop before the runtime removes the directory.

## Prepared instruction invocation

`AgentRunRequest.invocation` selects an exact implementation reference, named bindings, recipient source references and `production` or `experimental` purpose. It is accepted only with `caretaker` / `execute-motif@1`. Rust validates the request before starting the worker. The ordinary stored run request pins the selection and bindings across checkpoints and restart; inspection retains this attribution next to the actual effects and result.

`invocation.read` returns that run's authorized `Implementation` and invocation. Pi places the prepared policy beneath owner instructions and grants. Rust rechecks availability, required capabilities and execution authority before further active operations and model dispatch. Production requires contextual admission. Experimental purpose is a host run setting requiring sandbox mode; worker tools cannot set it. `registered_tool` implementations retain the existing `action.execute` path.

An instruction implementation needs `instruction_contract` for invocation. Its declared inputs accept strings, numbers, booleans, objects, arrays, granted artifact paths or granted tool IDs. Bindings are limited to 32 declared names and 64 KiB. The contract retains outputs, entry/exit obligations, limitations and exact discovery-record versions; `material` contains the conditional policy. These checks establish interface shape and capability availability, not semantic applicability. Existing stored instruction records remain readable; candidates without this contract cannot be invoked through the new path.

For `execute-motif@1` and `recombination@1`, Rust derives `Grant.prepared_run`; owners cannot register that field. Delivered roots are prepared definitions, implementations, memories and admissions, explicit recipient references, and the run's own observations. Donor event history, other runs' retained results and donor snapshots are withheld through the shared source checks, including direct RPC calls. Prepared material can depend on donor artifacts outside the recipient's paths without granting access to those artifacts. Ancestry withdrawal, scope and split restrictions still apply. Hosts must grant only actual recipient workspace paths; raw state directories are not source-authorized artifacts.

Nested invocation and inline donor investigation currently return explicit unsupported/denied results before queuing work. The host can start separately scoped investigation or invocation runs through the existing supervisor. This is the R5 acceptance option for unsupported nesting; it does not claim nested learned execution is implemented.

A `Transplant` may name `invocation_run`, `recipient_entry_refs` and `result_refs`. An executed transplant must match the actual run's selected donor version and bindings. Its references must be available to that invocation. An advisory transplant may omit execution fields; a narrative transplant alone does not establish that the implementation ran.

## Explicit record retrieval modes

`search.query` preserves literal `all_terms` matching, ID ordering, `offset` and `next_offset` by default. `query_mode: "any_terms"` broadens lexical matching; `order: "relevance"` uses FTS5 BM25 with ID tie-breaking. `function` filters the authored `Implementation.function` category exactly. `eligible: true` restricts candidates by granted tool capabilities and effect mode without requiring admission. `inventory: "usable"` continues to require contextual admission. Lexical rank and authored function labels do not prove compatibility.

Pages include `complete` and, when another eligible result exists, opaque `next`. Send `next` as `after`, preserve the query and filters, and use `offset: 0`. Cursors bind query, grant, prepared-run selection and index/source generation. Changed indexes require a fresh search; BM25 cursors also restart after other index writes because its document frequencies cover the index. Scope, retirement, expiry, source availability and eligibility are checked before any result body or returned count is presented. Exact-ID reads remain separate. Schema 20 adds index-generation triggers; no embeddings or external search service are introduced.

## Whole-agent laboratory

Host configuration may register `agent_evaluators` alongside existing command `evaluators`. `AgentEvaluator` runs ordinary Pi workers using `execute-motif@1`, exact implementation references and case bindings. It does not select task solutions from implementation names. Each case has its own project namespace and workspace. Host-created allocation ancestry links its restricted grant to the original case, arm, study and owner wallet. Worker RPCs cannot create these cross-grant funding or source-delivery relationships.

A case's `input.subject` contains only `prompt`, `files` and `bindings`. Other case input, including `oracle`, goes only to the protected judge after execution. Registered subject tools remain trusted host code; this boundary is a Ribosome capability boundary, not an operating-system sandbox for arbitrary executables. Keep judge code and credentials out of subject tools and granted paths.

`AgentEvaluatorConfig.stages` maps arm IDs to one to four host-owned stages. Each stage optionally selects an exact implementation; omission selects the experiment arm's implementation. Stages get separate Pi runs and equal portions of the case ceiling, while spending from the same aggregate wallet. Subsequent stages receive the preceding summary as task data, fresh receipt references and the latest branch. A stage that uses its allowance can be followed by a funded retry or caretaker. Cancellation and interruption stop further stages. A reviewer that makes no changes preserves the preceding branch. Cross-case learning retention is not supported by this adapter; `retain_learning_memory: true` is rejected. Existing command evaluators retain their explicit learning-workspace option.

Only the selected prepared records and starting memories can cross into a subject namespace. Donor ancestors remain available for withdrawal checks, without becoming readable inputs. Imported starting memory is read-only; a recipient can save its own derivative. The fixed starting version is checked on later delivery. Ordinary record, event and artifact scope checks remain in force.

`Experiment.study_objective` and optional `learning_cost` must match the host `AdmissionPolicy`. `function` checks the declared local quality and validity. `system_benefit` requires baseline, retry, critique, care and candidate arms. Its primary metric is `verified_success`, derived from the protected `passed` observation; a favorable auxiliary score cannot replace task success. Host stage configuration must start each arm with the same unchanged worker; retry repeats it, and the candidate arm subsequently executes its prepared behavior. A whole-agent policy requires `case_budget`. Legacy studies without an objective keep their existing pairwise admission rule.

The study freezes its record, implementation records, evaluator configuration, case inputs, policy and starting memory. Host model/tool version declarations must describe the configuration actually deployed. Protected family consumption is recorded by client/project/family during the same transaction that prepares the study. A fresh grant, experiment ID or policy ID cannot reuse that family as an untouched holdout. Known donor and starting-memory family lineage cannot overlap a protected recipient family. Family identity is an owner annotation of actual source lineage; renaming filenames or numbers is not a new family.

`Evaluation.run_refs` names actual stage runs. `execution_status` and `usage_complete` keep failed, exhausted and undispatched cases visible. A local case ceiling does not stop other funded cases. Shared-budget exhaustion or cancellation prevents further dispatch and preserves remaining matrix entries. Model task errors remain independently scored observations; they are not automatically library failures.

`ExperimentResult.report` contains observed arm means, verified-success counts and rates using the full planned denominator, observed/planned counts, measured secondary outcomes, study usage and paired comparisons. Repetitions are averaged within each case before a 2,000-resample, 95% percentile bootstrap. Fewer than two paired cases has no interval. The report states case/family counts and execution order; one repetition does not counterbalance order. Intervals describe these cases, not general reliability. System-benefit acceptance requires the preregistered improvement threshold against every control and complete usage. Missing outcomes remain inconclusive. Learning cost records observed `cost_microusd`, `complete`, and `reuse_count`; absent or incomplete learning cost is not silently treated as zero or amortized away.

The built-in agent adapter's judges are trusted offline commands. They return `EvaluationObservation` JSON with exit status zero for both passing and failing task outcomes; nonzero exit or timeout is evaluator execution failure. Optional `secondary_judges` receive the same protected observations; disagreement is retained and makes `passed` unknown. An LLM judge requires a host evaluator that meters those calls through `EvaluationAccount`; the offline-command configuration does not establish model-judge metering or semantic independence.

Archive cell quality is the mean of all designated repetitions for its measured member cases. Inconsistent cell membership across repetitions cannot select a lucky trial. Entries retain the exact implementation version, admission reference, complete evaluation set and restrictions. Withdrawn supporting evidence makes an entry unavailable. Schema 21 adds protected exposures, prepared source delivery for isolated evaluations, and aggregate archive evidence. Older archive rows without aggregate evidence are retained on disk but are not presented as supported aggregate elites.

### Integrated qualification boundary

The R7 installed consumer exercises both attachment and prepared invocation through the existing public interfaces. Recovery of an observed application does not grant permission for another write or automatically restore validation after its writer handoff is lost. A fresh authorized check may restore the current target's supported properties while leaving unvalidated dependents stale. The next provider request after memory retirement excludes that memory.

Qualification reports distinguish a completed process, complete accounting, passed task checks and supported benefit. An inconclusive discovery with no executable candidate leaves downstream evaluations unexecuted. Exported evidence preserves that distinction and does not publish raw provider configuration or hidden evaluator inputs. R7 changes no wire version or stored format.
